## 1. 環境セットアップ

- Node.js: LTS版を使用する。バージョンは`.nvmrc`/`package.json`の`engines`で固定・記録する（現状未整備、整備が必要）。
- Windows環境: リポジトリフォルダとnpmキャッシュをWindows Defenderの除外対象に追加する（`node_modules`内の大量の小ファイルに対するリアルタイムスキャンが遅延の主因）。
- パッケージインストール: lockfileが存在する場合は`npm install`でなく`npm ci`を使う。
- 依存関係の競合が出た場合、`--legacy-peer-deps`で隠蔽せず、まずバージョンピンでの解決を試みる。

背景・過去の躓きの詳細は`docs/lessons-learned.md`を参照。

## 2. ツールの役割分担

| ツール | 役割 |

| Claude.ai（本プロジェクトのチャット） | アーキテクチャ・設計判断、Claude Code向けプロンプト生成、エラー分析。「スーパーバイザー」役 |

## 3. コミット規律

- `git add .`は使わない。完了した作業単位ごとに対象ファイルを明示して`git add <file>`し、即座にコミットする。無関係な変更を混在させない。
- コミットメッセージは、何を・なぜ変更したかが分かる形で書く。

---

## 4. 中立性・編集ルール（再検討不可）

- 議会活動（質問回数・賛否・出席状況等）は評価・採点をせず、事実の記録に徹する。
- 選挙争点コンテンツは、賛否それぞれの論拠に対応するデータを対で示す。
- 議会だよりは、賛否一覧表（議案番号・件名・議員/会派ごとの賛否）という事実データの抽出にのみ使用可。ナラティブな要旨・解説部分は情報源として使用しない（議会広報委員会による編集物であり、中立性の観点から除外）。

## 5. Cursorとの作業（実行時制約の要約）

詳細ルールは`.cursorrules`に記載する（本節はその人間向け要約）。

- **環境変更コマンド（`npm install`/`npm ci`、パッケージの追加削除、`node_modules`削除等）を実行する前に、Cursorは必ず日本語で確認を求める。** 許可を得るまで、代替コマンドを含め他のコマンドも実行せず待機する（2026-08-04のCursor暴走事故を踏まえた対策）。
- 独立した新規タスクは**New Agent（クリーンコンテキスト）**で開始する。同一タスクの続きのときだけ同じチャットを継続する。前チャットの継続はコンテキスト消費・重複プロセスの原因になる。
- コマンドの承認は1件ずつ行う（「Always Run」は使わない）。
- 環境系コマンド（install/build）は極力エージェントに実行させず、人間がターミナルで実行する。

## 6. AI指示の品質ルール

Claude.ai・Cursor・Claude Codeいずれからも、人間（あなた、または将来のボランティア）へのコマンド提示は以下を満たす。

- コマンドは必ず、(1)どのツールの (2)どのパネル（Cursorのターミナル／Claude Codeのターミナル等） (3)どのディレクトリ（`cd`含む）で実行するかを明示する。PCに不慣れな人でも操作できる粒度にする。
- 「gitにpushして」等の抽象的な指示は禁止。`git add <具体ファイル>` → `git commit -m <メッセージ>` → `git push`を都度、具体的に提示する。
- コピー&ペーストで完結するよう、コマンドは1つのコードブロックにまとめる。
- 既存ファイルを修正する場合、差分比較を人間にさせない。「丸ごと上書きしてよい完全版」として提示し、配置先パスとgitコマンドをセットで出す。
- ファイルを生成して渡す際は、(a)作業環境にあるだけでリポジトリには未反映であること (b)配置先の具体的パス (c)`git add`/`commit`/`push`のコマンド、の3点を毎回明示する。
- 説明・理由の長文化を避ける。結論と手順を先に。理由は問われたときのみ。

---

## 7. 引き際ルール

- 深夜に`npm install`・ビルド確認・環境復旧など「終わりが読めない」処理でトラブルが発生した場合、20分経っても解決しなければその場で打ち切り、翌日の日中に再開する。粘って深夜まで付き合わない。

## 8. 自治体を1件追加する手順

前提: `docs/frontend-architecture.md`の動的ルート化が完了していること。**現状のルートは`app/gifu-pref/[city]/page.tsx`で、`gifu-pref`部分は固定リテラルのまま**（同文書「実装状況」節参照）。他都道府県の自治体を追加する際は、まずルーティングの拡張（都道府県も動的セグメント化するか、県ごとに同型のルートを増やすか）を先に決定する必要がある。

岐阜県内での自治体追加手順（現状の実装を前提）：

1. `python scripts/gen_municipality_master.py` を再実行する（手書きで `lib/municipalities.ts` や `data/municipality_master.json` を編集しない）。生成物をコミットする。
2. M1〜M3のデータソースに対象自治体のデータが含まれているか確認する（含まれていなければ該当データソースの取得スクリプトを対象自治体まで拡張する。無い場合は未整備表示のまま残す。0や仮値で埋めない）。
3. `npm run build`でエラーなくビルドできることを確認する。
4. 対象自治体のページが正しく表示されることを目視確認する。

## 9. ボランティア環境ヒアリングとタスク割当

新しいボランティアが参加する際は、以下をヒアリングした上でタスクと指示の粒度を決める。

- 環境: OS、RAM、Node.jsの有無、使用エディタ
- 習熟度: git習熟度、AIツールの契約状況

| 環境・習熟度 | 割当タスク | 指示の出し方 |
|---|---|---|
| 低スペック・初心者 | データレビュー等の読み取り中心（低リスク） | コピペで動く具体コマンドのみ |
| 中級以上 | UI実装・パイプライン | 通常の指示 |

改善提案（環境対策など）は「素人が実施可能・短時間・低リスク」に限定する（Defender除外、Node LTS導入、`npm ci`等）。管理者権限を要する重い変更やリスクのある提案はしない。
