## 1. 自治体マスタ（Single Source of Truth）

現状、M1/M2は市区町村名の文字列完全一致で照合し、M3のみ団体コードで照合している。名前キーは全国展開で衝突する（同名自治体、表記ゆれ）上、広域連合の保険者対応がページにハードコードされている。これを自治体マスタ1本に統合する。

### 1.1 フィールド定義

```
area_code          : 団体コード（6桁、全国地方公共団体コード）。primary key
pref_name          : 都道府県名
pref_slug          : URL用スラッグ
city_name          : 市区町村名
city_slug          : URL用スラッグ
kaigo_insurer_name : 介護保険者名（広域連合の場合は連合名。単独市町村なら市町村名と同一）
status             : "active" | "merged" | "abolished"
effective_from     : 有効開始日
effective_to       : 有効終了日（statusがactiveならnull）
successor_area_code: 合併・廃止時の承継先団体コード（履歴解決・リダイレクト用。C-8）
```

生成物置き場: `data/municipality_master.json`。手書き禁止、生成スクリプトを単一ソースとする。

### 1.2 広域連合対応

「もとす広域連合＝瑞穂市・本巣市・北方町」のような対応関係は、ページ側の定数（`KAIGO_INSURER_NAME = "もとす広域連合"`等）で持たせる現行方式を廃止し、マスタの`kaigo_insurer_name`フィールドに集約する。自治体を追加するたびにページ側で特別扱いを書く作業をなくすのがこの節の目的。

## 2. データ照合キーの統一

- 全指標データセット（M1〜M3・基礎データ層含む）に`area_code`を付与する。パイプライン（M1/M2抽出スクリプト）側で市区町村名→area_codeの名寄せを1回だけ行い、以降の実行時ロジックは`area_code`のみで照合する。
- `lib/metrics.ts`の全getterを`area_code`引数に統一する（例: `getKodomoIryohi(cityName)` → `getKodomoIryohi(areaCode)`）。市区町村名文字列での検索は廃止。
- 表記ゆれ（ヶ/ケ、旧字/新字、町/まち等）の吸収は、マスタ生成スクリプト内の名寄せ辞書に閉じ込め、実行時コードには持ち込まない。

## 3. ルーティング

- `app/[pref]/[city]/page.tsx` の単一動的ルートに統合する。既存の手書きページ（`gifu-shi/page.tsx`、`mizuho-shi/page.tsx`）はこの節の実装完了時に廃止する。

### 3.1 カード構成のデータ駆動化

「どのカードを・どの順で・どのタイトル/出典/noteで出すか」を、ページJSXの直書きからカードレジストリ（例: `lib/card-registry.ts`）に外出しする。出典文字列・更新日は既にメトリクスのメタ情報に入っているため、ページ側に直書きされている出典文字列（「こども家庭庁 実施状況調査」等）もメタ由来に統一する。

この節が完了すると「自治体を1件追加する」作業は、マスタに1行（area_code）を足すだけになる。ボランティア運営の前提はここで初めて成立する。

## 4. 欠損データの扱い（throw廃止）

現行は指標欠損時に`throw new Error(...)`しており、`output: 'export'`では1自治体・1指標の欠損がビルド全体を落とす。1,700自治体展開では欠損が常態のため、この設計は維持できない。

### 4.1 内部状態（多値）

```
present          : データあり
not_applicable   : 制度上・構造上該当しない（例: 広域連合未加入市町村への単独介護保険料）
not_yet_collected: 未収集（パイプライン未着手）
fetch_error      : 取得失敗（上流URL 404、タイムアウト等）
parse_error      : 取得はできたが構造解析に失敗
```

判定は自治体マスタとパイプラインが実行前に確定する（a priori）。スクレイプ結果からの事後推測には頼らない。

### 4.2 表示ルール

- `present`以外はthrowしない。カードごとに欠損理由に応じて描画をスキップ・分岐する。
- UI表示は2〜3段階に丸めてよい（例:「該当なし」「未整備」）。ただし`fetch_error`/`parse_error`は「データなし」として一般公開画面に出さない。
- `fetch_error`/`parse_error`は公開をブロックし、直前の正常データ（last-good）を保持したままビルド通知を出す（詳細は`docs/operations-runbook.md`）。取得失敗と正当な不在を混同すると、パイプラインの故障が「データなし」として静かに公開され続ける事態を招く。

## 5. URL永続ポリシー

原則: 公開後のURLは変更しない。自治体Watchは外部からの引用・被リンクを前提とするプラットフォームであるため。

本節は2026-08-07セッションで確定した（旧5.1「未確定事項」を解消）。裁定サマリは`docs/20260805_decisions.md` F節（決定#6・C-8確定）を参照。

### 5.0 URLとarea_codeの関係（前提）

- 公開URLは人間可読スラッグ `/{pref_slug}/{city_slug}/` で構成する。area_codeはURLに含めない。
- area_codeは自治体マスタ上の**結合キー**であり、「表示スラッグが変わっても旧スラッグ→新スラッグを解決するための内部キー」として機能する。
- area_codeは合併・廃止で改番される（同一エンティティが存続する間のみ不変）。したがって「団体コード基準の恒久URL」とは、(a) 同一エンティティの改称に対するarea_code結合キー解決、(b) 合併・廃止に対するsuccessor_area_code連鎖解決、の**2機構の総称**である。area_code単独では合併をまたぐ恒久性を保証しない。

### 5.1 スラッグ凍結ポリシー（公開前必須）

- 公開したスラッグは凍結する（append-only）。公式名称変更等の実データ発生時を除き変更しない。
- 凍結の前提としてスラッグ規約（5.4）を公開前に確定する。規約が先行しないと、後日「規約整備のための一斉変更」という、本ポリシーが防ごうとしているchurnを自ら発生させる。
- 例外的なスラッグ変更はログを残し、5.2の機構で旧URLを維持する。

### 5.2 リダイレクト実装方式（output:'export'整合）

- **採用**: 静的HTMLリダイレクトstub（meta refresh + `rel=canonical` + JS `location.replace`）。`out/`内の実ファイルとして生成するため、Vercel / Cloudflare Pages / GitHub Pages いずれでも同一に機能し、ホスティング非依存原則（0節・`out/`無改変ポータビリティ）を崩さない。
- **却下**: `next.config`の`redirects()`（`output:'export'`非対応）。host固有config（`vercel.json` / `_redirects`）を**主機構**とする案（原則違反。`vercel.json`はVercel専用、`_redirects`はCloudflare/Netlify専用でVercelは無視、GitHub Pagesは両方非対応）。
- **任意拡張（V2前・SEO最適化）**: 現ホストでtrue 301が測定上必要と判断した場合のみ、マスタから`vercel.json`のredirectsを生成し重畳してよい。V1必須ではない。stubの`rel=canonical`によりリンク評価は概ね継承される（C-7と連携）。
- stubは**マスタ駆動のpost-buildスクリプト**で生成する（退役エントリを走査し旧path→現行pathのHTMLを`out/`へ書き出す）。退役スラッグはactiveなルート集合に不在のため`dynamicParams=false`と両立する。

### 5.3 合併・廃止時の解決（successor_area_code / C-8確定）

- statusが`merged`/`abolished`のエントリは、successor_area_codeを辿り現行activeな終端エンティティまで**ビルド時に推移解決**する（多段合併を1ホップのリダイレクトに畳む）。生成時にサイクル検知と `successor.effective_from ≥ predecessor.effective_to` の整合検査を行う。
- **既定挙動 = リダイレクト**: 旧自治体URL→承継先URLのstubリダイレクト。旧ページは消滅する。
- 旧自治体の合併前データJSONはリポジトリに残るため、本挙動は不可逆ではない。「合併アーカイブ層」（旧自治体の凍結スナップショット＋承継先への導線）はV2以降の任意コンテンツ機能として記録し、本永続機構とは分離する（必須項目である本ポリシーを、nice-to-haveであるアーカイブ層の後ろに置いて公開を遅らせない）。

### 5.4 スラッグ規約（公開前確定・凍結）

本節は2026-08-07セッションで凍結した。以降、実データ（公式名称変更・合併）以外を理由とする改定は行わない（規約整備のための一斉変更を自ら誘発するため）。

**5.4.0 使用文字**
- スラッグは小文字 `a–z` とハイフン `-` のみ。数字はタイブレーク(5.4.5)のarea_code付与時に限り許容。
- アポストロフィ・マクロン・その他記号は使わない。撥音nの扱いは5.4.2で規定。

**5.4.1 ローマ字化方式**
- ヘボン式（旅券・道路標識の実用ヘボン式）。訓令式は不可（岐阜=gihu等になり不自然）。
- かな→ローマ字はヘボン式標準（し=shi、つ=tsu、ふ=fu、じ=ji、ち=chi、しゃ=sha 等）。

**5.4.2 撥音・促音・長音**
- 撥音「ん」は文脈によらず常に `n`（現代GSI式）。伝統ヘボン式のb/m/p前=mは採らない。実例：安八町 = anpachi-cho（ampachiとしない）。
- 促音「っ」は後続子音を重ねる（例：別府=beppu）。
- 長音は延長表記を用いず単母音に畳む（おう・おお→o、うう→u）。実例：大垣=ogaki、郡上=gujo、養老=yoro。えい等の慣用が確立した語や形態素境界をまたぐ語は機械変換で一律処理せず、5.4.6の権威ソースのカナに従い、必要時は名寄せ辞書で上書きする。

**5.4.3 接尾辞**
- `-shi`(市)/`-ku`(区)/`-cho`・`-machi`(町)/`-son`・`-mura`(村) を、当該自治体の公式読みに従いハイフン区切りで付す。
- 町の-cho/-machi、村の-son/-mura は推測しない。5.4.6のカナ列の読みを正とする。
- 読みが自明でない岐阜の実例：
  - 神戸町 = **godo-cho**（ごうど。「こうべ」ではない。漢字からの機械推測は誤る）
  - 白川町(加茂郡)=shirakawa-cho、白川村(大野郡)=shirakawa-mura（同綴りだが接尾辞で分離。5.4.5の衝突に至らない実例）
  - 七宗町 = hichiso-cho（ひちそう）、坂祝町 = sakahogi-cho（さかほぎ）

**5.4.4 県スラッグ規約**
- 形式：`{県名核のヘボン式ローマ字}-pref` に統一（gifu-pref、tokyo-pref、osaka-pref、kyoto-pref）。
- 都/道/府/県の別はURLに含めない。to/do/fu/kenの区別は表示層の責務とし、URLは「pref」で一様化する。理由：(1)生成規則と心的モデルの単純化、(2)北海道の病理（hokkai-prefは通じない／hokkaido-doは不合理）の回避、(3)既公開がgifu-prefのみで移行コスト0。
- 唯一の明示例外：北海道は核名を切り出せないため慣用ローマ字を一体で用い **hokkaido-pref**（do+prefの意味的重複は許容。hokkai-prefは不可）。
- 規約は凍結。他46県への適用は各県の実装時（完全動的ルート化）に行う。適用の繰延であって規約の未確定ではない。

**5.4.5 県内スラッグ衝突のタイブレーク**
- 定義：同一県内で「ローマ字綴り＋接尾辞」が完全一致する稀ケース（岐阜は該当0件。白川町/白川村は接尾辞で分離済み）。
- 一次：町村は郡名をprefix（`{郡ローマ字}-{名}-{接尾辞}`）。町村は住所上つねに郡に属し、郡が自然な人間可読の識別子であるため。
- 二次（郡prefixでも衝突、または郡を持たない市同士の衝突）：area_codeを接尾辞化（`{名}-{接尾辞}-{area_code}`）。一意性の機械的な最終保証。
- 該当0件でも予防として凍結（全国展開で衝突が出た時に規約が後追いにならないため）。

**5.4.6 「公式読み」の権威ソース（未確定事項#4の確定）**
- 一次ソース：**総務省「全国地方公共団体コード」の『都道府県名（カナ）』『市区町村名（カナ）』列**（団体コードをキーとする）。
- 選定理由：(1) 識別子が団体コード＝結合キー(area_code)と同一で、コード・漢字名・カナ読みが1ファイルから同時に取れる（DRY）。(2) カナ列は接尾辞の読みを含む（例：神奈川県＝ｶﾅｶﾞﾜｹﾝ）ため、5.4.3の-cho/-machi・-son/-muraの読み分けを同一ソースで解決できる。(3) 単一の機械可読ファイルで全国O(1)。合併・改称時は同省の改正一覧表で更新され、C-8のsuccessor追跡と同じ更新系列に乗る。
- 扱い：カナは半角カタカナ（例：ﾎｯｶｲﾄﾞｳ）。全角正規化→ヘボン式変換のヘルパーを名寄せ辞書生成スクリプトに置く。長音はカナがウ/オで綴るため5.4.2で単母音化する。
- 例外時の権威：総務省カナに誤り、または自治体が自ら別読みを宣言している場合に限り、当該自治体の例規・公式サイトを正とし、名寄せ辞書に上書きエントリ（漢字→カナ→スラッグ・根拠URL付き）を記録・ログ化する。既定は常に一次ソースに従う。

### 5.5 V1での適用範囲（実装の繰延）

- V1（岐阜・2自治体・公開前）時点で実在すべきリダイレクトは0件（改称・合併ともに未発生）。本フェーズの成果はポリシー（5.0–5.4）の確定であり、stub生成スクリプトの実装は「最初の退役/改称の発生」または「完全動的ルート化」のいずれか早い時点まで繰延してよい。
- 公開前に凍結すべきは規約（5.4）と公開済みスラッグ（`gifu-pref` / `gifu-shi` / `mizuho-shi`）であり、リダイレクト機構の実装ではない。

### 5.6 地理階層・ルート構成・予約セグメント（2026-09-13確定）

確定日: 2026-09-13。位置づけ: §5.0・§3・§5.4を地理階層と地域/政府分離に合わせ具体化。UI側正本は `ui-vi-handoff.md` §0.13。**§5.0「人間可読スラッグ・area_codeはURLに含めない」は不変。**

**5.6.1 リソースの分離**
- 地域（area）：`/{pref-slug}/`（例 `/gifu-pref/`）。一覧・地図・比較・政府への導線。
- 政府（government）：`/{pref-slug}/{gov-slug}/`。県庁と市区町村を**同一規約**でスラッグ化。
  - 県庁＝県名＋県接尾辞（`gifu-ken`/`tokyo-to`/`hokkaido-do`/`osaka-fu`/`kyoto-fu`）。§5.4.3を県へ拡張。
  - 市区町村＝§5.4.3のとおり（`gifu-shi` 等）。
- `-pref`（地域）と `-to/-do/-fu/-ken`（政府）は別リソースの綴り。同一県から2綴りが出るのは設計どおり。

**5.6.2 ルート構成**
```
/{pref}/                         地域ページ            app/{pref}/page.tsx
/{pref}/{gov}/                   政府入口（4入口）     app/{pref}/{gov}/page.tsx
/{pref}/{gov}/{tab}/             各入口情報            tab ∈ machi|gyosei|gikai|kurashi
/{pref}/{gov}/trends/{cardKey}/  経年（カード従属）
/search/                         検索結果（#q= をクライアント読取。§7。2026-10-06 ?q= から変更＝検索語を外へ送らないため・launch-backlog.md D-5。旧形式 ?q= も読む）
```
- V1は `{pref}`=`gifu-pref` 固定リテラルのまま可（完全動的化は `pre-launch-blockers.md` #2）。本節は構造確定であって固定リテラル解消の前倒しではない（D-17）。
- 既存の県情報 `app/gifu-pref/[tab]/` は県庁配下 `app/gifu-pref/gifu-ken/[tab]/` へ移す（未公開ゆえ移設は無コスト・リダイレクト不要。§5.5）。

**5.6.3 経年URL＝カードキー駆動（[category]直書きの廃止）**

### 5.8 多言語版のURLの形（2026-10-11 運営者裁定。決めるのは形だけ・V1では実装しない）

位置づけ: 多言語版（英語版等）を作るか、いつ作るかは未決。公開後はURLを変えない決まり（§5.1）があるため、後から追加しても既存URLが壊れない形だけを公開前に固定する。

1. **日本語は今のURLのまま。** 日本語を `/ja/...` へ移さない（公開後に全URLが変わるため）。
2. **他の言語は、URLの先頭に言語の印を付ける。** 印の後ろは日本語と同じ形。例 `/en/gifu-pref/gifu-shi/machi`。印は BCP 47 の言語タグを小文字で書く（`en`・`ko`・`zh-hans` 等）。
3. **URL名（スラッグ）は訳さない。** `gifu-shi` 等は全言語で共通。言語ごとにスラッグを持つと、凍結の対象が言語の数だけ増える。
4. **言語の印は予約語**（§5.6.4）。
5. **言語の切り替えはリンクで行う。** 見る人の言語を自動判定して振り分けることはしない。理由は2つ。(a) 自動判定にはサーバー側の処理（Middleware）が要り、§0「ISR・API Routes・Server Actions・Middlewareは使用しない（ホスティング非依存の原則）」に反する。(b) 検索エンジンの公式案内（Google 検索セントラル「Managing Multi-Regional and Multilingual Sites」）自体が、自動の振り分けを避け、他の言語版へのリンクで選ばせるよう勧めている。各ページには他の言語版の場所を伝える印（hreflang）を付ける。
6. **実装しない。** V1では何も実装しない。実装するとき（別途裁定）に、次を確認する: (a) 画面の文言の切り出し（現状は日本語が54ファイル・約865行に直書きで、`<html lang="ja">`・数字の書式 `ja-JP` も固定）、(b) JSONの日本語表記（期間・注記）の訳の持ち方、(c) 検索（読み照合）の言語対応、(d) 配信先のファイル数上限（無料2万／有料10万。言語を1つ足すごとにページのファイル数はほぼ倍）、(e) 訳文への訂正方針・中立性の適用。

## 6. 静的生成のスケール方針

1,700自治体×複数ページで数千〜1万ルート規模になるが、Vercel無料枠（100h/月・45分/build）には抵触しないと判断する（全件SSG堅持、decisions.md 決定事項#11）。真のボトルネックはページ数そのものではなく、ページ単位のJSペイロード（Rechartsハイドレーション）とビルド時間である。

> **2026-10-05 注記**：公開先は Cloudflare に変更（`20260808_decisions.md` D-22）。制約は「1つの配信先に置けるファイル数（無料2万／有料10万）」に移った。実測では1自治体あたり約38ファイル（うち約8割はページ移動用の補助ファイル）で、全国約6万8千の見込み。ビルド時間は349ページで16秒。

- V2着手時に、per-pageのJSペイロードとビルド時間を実測する。目安として1ページ100KB超を要注視ラインとする。
- 継続/移行の判断閾値（目安）: 〜1万ページは現行継続、1〜5万ページで実測して判断、5万超で分割ビルドまたはSSR方式を検討する。
- 移行候補としてAstro（ゼロJS＋チャート部分のみislands化）を記録する。ただしV1でのNext.js継続を否定するものではない（decisions.md B-4、GPT提案のtiming採用・即移行案は却下済み）。

## 7. 検索の名寄せ・マッチング（実装仕様）

確定日: 2026-08-26。位置づけ: `docs/ui-vi-handoff.md` §2.4で確定した検索の**挙動**（団体コードを本体ID／表示は正式名称・正規化は検索キーのみ／読み検索／例外異体字のみ手動辞書／クライアント検索でスケール）を前提に、その**詳細アルゴリズム**を実装仕様として一次記録する。ui-vi-handoff §2.4未確定事項#13の帰結。本節は§1（自治体マスタ）・§2（照合キー）・§5.4.6（読みの権威ソース）に依拠し、これらの規律を新たに変更しない。

本節は**目標設計（実装仕様）**であり、現行の稼働検索がどの段まで実装済みかは実コード確認事項。到達すべき仕様を定義する（実装状況節と同じ扱い）。

### 7.0 前提として崩さないもの（再掲・参照）

- **本体IDは団体コード（area_code）**：自治体の同一性は名称でなくarea_codeで判定する（§1 primary key）。同名（府中市＝東京都/広島県）は別コードで区別し、両方を必ず表示する（ui-vi-handoff §2.3／§2.4）。
- **表示名は不変・正規化は検索キーのみ**：機械正規化・辞書・読み変換はすべて「検索キー／スラッグ」に対してのみ行い、画面表示用の正式名称は一切変換しない（§2・§5.4系と同型）。
- **読みの権威順序は§5.4.6を踏襲**：既定＝総務省「全国地方公共団体コード」カナ列。例外時のみ自治体例規・公式で上書き。本節はこの順序を変更しない。
- **クライアント検索・静的エクスポート整合**：検索インデックスは小さくブラウザ側で完結する（DB不要、`output:'export'`整合。ui-vi-handoff §2.4・§6）。

### 7.1 マッチ評価順（6段）

利用者入力（正規化後の検索キー）に対し、以下の順で候補を判定する。**この順序は「入力と識別子の一致の厳密さ（string-match specificity）」の機械的順序であり、自治体そのものへの評価・総合スコア・ランキングではない**（`20260808_decisions.md` D-6／ui-vi-handoff §2.3中立性）。

1. **完全一致**：正規化検索キー＝正式名称の正規化キーが完全一致。
2. **読み一致**：正規化検索キー＝読み（カナ／ヘボン式ローマ字）の正規化キーが完全一致（「まち/ちょう/むら/そん」等の接尾辞読みを含む。§5.4.3）。
3. **異体字一致**：機械正規化で吸収しきれない異体字・通称を、名寄せ辞書（7.2）の別名エントリ経由で一致（例：塩竈／塩竃／塩釜）。辞書は area_code に紐付く。
4. **前方一致**：検索キーが正式名称または読みキーの先頭に一致（例：「岐」→岐阜県・岐阜市…）。
5. **部分一致**：検索キーが正式名称または読みキーの一部に一致。
6. **誤字候補**：上位段で0件または僅少のとき、編集距離に基づく「もしかして」候補を最後段として提示する（軽微な打鍵誤りの救済）。

- **段内の並び**：同一段に複数該当した場合の並びは団体コード昇順（機械的順序。ui-vi-handoff §2.3、D-6）。段をまたぐ場合は上位段を先に置く。段順・段内順とも編集的な順位付け（総合スコア）を作らない。
- **同名の扱い**：同名複数（府中市）は該当段で両方を候補化し、都道府県名＋パンくずを併記して区別する（ui-vi-handoff §2.3）。片方を落とさない。
- **段の丸め（表示）**：オートコンプリートと検索結果ページでどの段まで出すかはUIの表示密度判断（ui-vi-handoff §2.3）に委ね、本節は判定順序を定義する。誤字候補は「もしかして」枠として他段と視覚的に分離してよい。

### 7.2 名寄せ辞書の生成手順（ビルド時・単一生成スクリプト）

名寄せ辞書と検索インデックスは、`data/municipality_master.json`（§1）と同じ権威ソースから**ビルド時に生成**する。手書き禁止・生成スクリプトを単一ソースとする規律（§1・§2）を検索インデックスにも適用する。実行時（ブラウザ）は生成済みインデックスの参照のみを行い、正規化ロジックを実行時コードに持ち込まない（§2）。

生成手順：

1. **権威ソースを団体コードで読み込む**（7.3）。各団体から area_code・正式名称（漢字）・読み（カナ）を取得する。

実装スクリプト：`scripts/gen_gifu_kana.py`（全国municipality_kana.jsonの生成。D-17に基づき収集は岐阜限定ではなく全国全件が対象）。再実装前に本ファイルの存在を確認すること（既存資産の未確認による重複生成を防ぐ）。
2. **検索キーを機械生成する**：正式名称の正規化キー（ヶ/ケ・旧字/新字・町/まち・全角/半角・カナ半角/全角の吸収）と、読みキー（カナ、および§5.4.1〜5.4.2のヘボン式ヘルパーで生成したローマ字）を、いずれも**検索キーとしてのみ**生成する。表示名は変換しない。
3. **異体字・通称の例外エントリを付す**：機械正規化で吸収しきれないものだけを、area_code に紐付けて手動追加する（漢字→カナ→別名キー・根拠URL付き、ログ化）。既定は常に一次ソースに従い、例外の上書き権威は§5.4.6に従う（自治体例規・公式のみ）。
4. **0件入力からの拡充（受け口のみ）**：検索ログの「0件になった入力」を、必要な別名だけ3の例外エントリに追加する原資とする。**ただし検索ログ収集自体はプライバシー・セキュリティの領域**であり、収集設計（個人非特定の集計・プライバシーポリシー記載）は`docs/security-model.md`側へ申し送る（ui-vi-handoff §2.4／未確定#14）。本節は辞書側の受け口を定義するに留める。
5. **クライアント検索インデックスを出力する**：area_code をキーに、表示用の正式名称と検索キー群（正式名称キー・読みキー・別名キー）をまとめた小さなインデックスを出力する。インデックスは静的アセットとして配信し、ブラウザ側で7.1を評価する。

### 7.3 データソース選定（権威順序は§5.4.6を踏襲）

- **一次（既定・権威）**：総務省「全国地方公共団体コード」。area_code・漢字名・カナ読みが1ファイルから団体コードをキーに同時取得できる（§5.4.6）。**正式名称・読み・コードの正はこのソース**。
- **補完（裏取り・読みの拡充）**：e-Stat「市区町村名・コード」、デジタル庁アドレス・ベース・レジストリ（ABR）。読みの補完とコードの突合にのみ用いる。
- **上書きしない規律**：補完ソースは一次ソースの値を上書きしない。不一致が出た場合は総務省を正とし、差分はログして例外エントリ（7.2-3）の検討対象とする。**値の上書きは§5.4.6の例外権威（自治体例規・公式）に限る**。この順序は§5.4.6と同一であり、本節で新たな権威を追加しない。

### 7.4 スケール（再掲・参照）

自治体名・読み・コードのインデックスは1,700自治体規模でも小さく、ブラウザ側クライアント検索で完結する（ui-vi-handoff §2.4、§6スケール方針）。Pagefind等の段階策はこの規模では当面不要。段の評価（7.1）もインデックス全走査で足りる規模である。

### 7.5 検索設計仕様の採用（2026-09-13）

`自治体Watch_自治体検索設計_実装仕様` を本§7の実装仕様として採用する。正規化・マッチ評価（完全→読み→別名→前方→部分）・同名両掲・団体コード昇順・クライアント検索・textContent/encodeURIComponent は §7.0〜§7.3・D-6・ui-vi §2.4 と整合。

**整合のための2点の上書き：**
1. **URLはスラッグ**。採用仕様の例示（`/prefectures/21/`・`/municipalities/212016/` のコード式）は用いない。検索レコードの `url` に §5.6 のスラッグURLを格納（検索ロジックは `url` を読むだけで無改修）。

誤字候補（§7.1-6）は採用仕様に無い＝V1は前方・部分一致まででよい。編集距離tierはV2。

**このビルドにページがある未公開団体（2026-10-18・`launch-backlog.md` L-9）**：索引 `data/search_index.json` は公開スコープ（岐阜）だけを published=true にし、試作の URL は書かない。`app/search/layout.tsx` がビルド時に、索引で published=false だがこのビルドにページがある団体を団体コード（市区町村・区＝area_code、県＝pref_code）で拾い、URL（索引と同じ末尾 / の形）を `components/SearchExtraPages.tsx` の入れ物で検索ページへ渡す。検索ページはその団体を「自治体ページ」としてリンクにする。公開用ビルドでは該当0件で入れ物を出さない（出力不変）。試作の県を公開に加えるときは、索引側（`scripts/gen_search_index.py`）で published=true にするか、この仕組みのまま公開ビルドにページを入れるかを決める。
