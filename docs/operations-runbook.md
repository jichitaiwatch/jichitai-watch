## 1. 更新カレンダー（`update_calendar.yaml`）

機械可読ファイルとして`update_calendar.yaml`をリポジトリ直下に置く。フィールド定義：

```yaml
# update_calendar.yaml の1エントリの構造
- source: string        # データソース名（例: "M1 こども家庭庁"）
  cadence: string        # 更新周期（例: "yearly", "3years", "monthly"）
  expected_publish_month: string  # 上流の公表予定月（例: "12月頃"）
  last_fetched: date     # 最終取得日
  next_check: date       # 次回確認予定日
  script: string         # 取得スクリプトのパス
  status: string         # "fresh" | "stale" | "check_needed"
```

## 2. 自動化の境界

V1規模（岐阜県内42市町村・3指標）では完全自動化は不要と判断する。

- **現状〜V1**: `update_calendar.yaml`のnext_checkを過ぎたソースを人間が確認し、半自動フェッチ（既存スクリプトを手動実行）→差分レビュー→手動コミット。
- **V2目標**: GitHub Actionsが定期的にPythonスクリプトを実行し、取得結果を新規ブランチ・PRとして起票。**人間がdiffレビューしてマージする**運用にとどめ、政府データの自動マージは行わない（上流ファイルの不正・破損が無審査で公開サイトを汚すリスクを避けるため）。
- 閾値ベースの異常検知（前年比の急変・行数減少・スキーマ変化・fetch失敗）を導入し、閾値を超えた変化のみ人間レビューを必須化、閾値内は迅速にマージしてよいとする案は**V2で検討**（decisions.md 決定#4）。V1では全件人間レビューとする。

## 3. 鮮度の可視化

`update_calendar.yaml`のnext_checkを過ぎた「stale」ソースを一覧するページ、またはビルド時警告を用意する。

- V1: ビルドログに「stale」ソース一覧を出力する簡易チェックスクリプトで足りる。
- V2以降: サイト上に鮮度ステータスを表示し、利用者に対しても「このデータは最終更新いつ時点か」を透明化する（運用ツールと信頼材料を兼ねる）。

## 4. 回帰検出

再取得のたびに前回JSONとの差分を取り、大きな変化を人間レビューに回してから公開する。

- 「大きな変化」の定義例: 数値が前年比で±30%以上変動、対象自治体数が前回より減少、必須フィールドの欠落。
- kaigiroku.net向けに実装済みの打ち切り検知ヒューリスティック（`docs/v2-gikai-pipeline-handoff.md`参照。件数がキリの良い数字の場合に警告）は、複数年で同一件数が続くケースを検知できない既知の穴がある（中津川市の事例で実証済み・実害なしだったが未解消）。この設計思想を全ソース共通の差分チェックへ一般化する際は、この穴を踏まえて改善する。

## 5. 上流URL消失・404への対応（decisions.md C-6）

議会パイプライン設計（`docs/v2-gikai-pipeline-handoff.md` 1.4節）で既に定めているログ形式・判断フローを、M1〜M3を含む全データソース共通のルールに昇格する。

### 5.1 検知時の挙動

- スクレイパー/取得スクリプトは404・5xx・タイムアウトを検知したら**自動リトライで押し切らず**、即座にログを出して停止する。
- ログ形式（既存の議会パイプライン向け書式を流用）:

```
[要人間判断] source=(データソース名) url=(該当URL)
発生日時: (日時)
HTTPステータス: (404/5xx等)
想定原因: 上流ページ構成変更 / 一時的な障害 / URL移転
求める判断: 代替URLの探索、または該当ソースの一時停止
現在の状態: 自動リトライは停止済み。他ソースの処理は継続中。
```

- 通知先（Issue起票・Slack等)は運用開始時に確定する。V1個人運用時点ではローカルログの確認で足りるが、ボランティア複数人運用に移行するタイミングで通知の仕組みが必須になる。

### 5.2 公開への影響

`docs/frontend-architecture.md` 4節で定義した`fetch_error`/`parse_error`状態と連携する（現状パイプライン未実装、V2目標）。実装後は、fetch_error/parse_errorが発生したデータについては**直前の正常データ（last-good）を保持したまま公開を継続し、当該箇所のみ更新をブロックする**。サイト全体の公開停止は行わない。

## 6. データ系譜（decisions.md C-2、決定#8）

系譜メタ（`source_url`・`fetched_at`・`source_file_hash`）のフィールド定義・JSON上の配置（トップレベル `sources` 配列）・キャッシュ機構下での `fetched_at` 意味論の正本は `docs/data-schema.md` 5節に一本化した（旧版は本節とdata-schema.md 5節でフィールド定義が重複していたため整理）。本節は運用ルール（取得頻度・遡及方針・差し替え検知との連携）のみを扱う。

- **遡及（公開前必須）**: #8は公開前必須のため、既存M1〜M3にも系譜メタを入れる。ただし再ダウンロードはしない。`fetched_at`は現行の手書き`updated`の日付（M1=2026-08-03 / M2=2026-08-06 / M3=2026-07-31）でbackfillする——再取得すると`fetched_at`が原初取得時刻でなくなるため（詳細は`docs/data-schema.md` 5.3・5.4）。作業は3JSONへの一度の追記で完了し、継続的な遡及は発生しない。
  - 旧版の「新規指標追加時からの適用を優先し、既存3指標への遡及は避ける（再取得コスト回避のため）」という方針は本節で撤回する。対象ソースは小容量・安定publication（年次/3年次）で、遡及は再ダウンロードなしのメタ追記のみのため再取得コストは実質ゼロ。#8が公開前必須である以上、遡及を優先する。
- **取得頻度と系譜は別問題**: #8は「過去に取得した事実の記録」であり、再取得のcadenceを決めるものではない。年次データ（M1/M3=年1回、M2=3年ごと）が公開後1年以内に古いのは正常運転であり、そのこと自体は#8の対象外。鮮度・再取得のcadenceは本文書1節（更新カレンダー）・3節（鮮度の可視化）が持つ。
- **差し替え検知との連携**: `source_file_hash`はキャッシュのバイト列から取得のたびに再計算し、前回出力JSONに記録された旧ハッシュと比較する。不一致は上流ファイルの差し替え・訂正を意味し、本文書4節（回帰検出）のトリガーの一つとして扱う（追加の監視インフラ不要）。
- **状態の正本**: 系譜メタ（#8）の実装状況は `pre-launch-blockers.md` #8 で確認する（本節は状態値を持たない）。
