## 1. スキーマ検証（decisions.md 決定#13、B-2裁定）

数値そのものが製品である以上、欠損を「—」やゼロで静かに吸収する（silent absorption）のはビルド失敗より悪いという判断による。

- **V1**: 軽量JSON Schema検証を導入する。各JSON（`m1_kodomo_iryohi.json`等）に対応するスキーマ定義を用意し、ビルド前（またはパイプライン実行後）に検証する。不整合はエラーとして検知する（サイレントに通さない）。
- **V2**: GitHub Actions上のCI検証に格上げする。
- **V3**: `schema_version`フィールドの導入は、外部コンシューマ（自治体Watch以外がこのJSONを直接参照する場面）が発生した時点まで後回しにする。V1〜V2では単一リポジトリ内で完結するため優先度は低い。

### 1.1 検証ツールの選定（未確定）

TypeScript側の型とスキーマ検証を単一ソースから生成する方式（pydantic/JSON Schema→quicktype等でTS型生成）が候補。パイプライン（Python）側とフロントエンド（TypeScript）側で二重定義にならない構成を優先する。具体的なツール選定はV1実装時に決める。

## 3. 全国順位・類似団体比較の集計段階（1-F）

カード仕様（`content-spec-v1.md`）は全国順位・類似団体比較を要求しているが、現データ・現コードに順位フィールドはない。横断集計は静的JSONの描画時には計算できないため、パイプライン側に集計段階を追加する。

### 3.1 設計方針

- 都道府県ページ・市区町村ページの二層設計と整合させる：順位は**市区町村レベルの全国横断比較**として設計する（都道府県ページはM1〜M3を集計しないという既存確定事項、CLAUDE.md 2026-08-04と矛盾しない）。
- パイプラインの最終段階として、収集済み全自治体のデータから各指標の順位・百分位を算出し、各自治体JSONに書き戻す。
- **区分マスタの結合・区分平均の算出・母集団の扱い・出力スキーマ拡張の詳細設計は `docs/similar-group-aggregation-design.md`（2026-08-29）に委譲する。** 本§は順位フィールドの置き場（§3.2）と二層設計との整合・正直ラベルを正とし、集計の式・区分束ね写像・comparison スキーマは当該設計書を参照する。

### 3.2 フィールド定義（案）

```
rank            : 収集済みデータ内での順位（整数）
rank_out_of     : 母数（収集済み自治体数）
percentile      : 百分位（0-100）
```

- V1時点では収集自治体数が少ない（岐阜県内42市町村）ため、「収集済みN件中の順位」であることをUI表示上も正直にラベルする（例:「県内順位」であり「全国順位」ではない旨を明示）。全国順位を謳うのはM1のような全国データを取得済みの指標に限定する。

## 5. データ系譜（decisions.md C-2・決定#8）

取得元URL・取得日時・取得ファイルハッシュを保存し、数年後に「この数値はどのファイルのどの版から出たか」を再現できるようにする（再現性の背骨）。**フィールド定義・配置・キャッシュ下での意味論の正本は本節とする。** `docs/operations-runbook.md` 6節は運用ルール（取得頻度・遡及方針）のみを扱い、フィールド定義は本節を参照する（旧版で重複していたフィールド列挙は6節から削除する）。

### 5.1 フィールド定義

系譜メタはJSONファイル単位でトップレベルに `sources` 配列として持つ。配列の各要素が1つの取得元ファイルに対応する。

```
sources: [
  {
    role             : そのファイルの役割ラベル（複数ソース時の識別用。単一ソースなら省略可）
    source_url       : 実際に取得したファイルの直URL
    source_page      : 人間可読な出典・公表ページURL（引用用。任意）
    fetched_at       : そのファイルを実際にダウンロードした時刻（ISO 8601）。原初取得時刻を保存する
    source_file_hash : 取得ファイルのバイト列の SHA-256
  },
  ...
]
```

- `sources` の要素数は取得元ファイルの本数に対応する。M1（全国一括PDF 1本）・M2（XLSX 1本）は1要素、M3（市/町村 × 概況/目的別/性質別の6本）は6要素。
- 既存の単数 `source` ／ M3の `soumu_urls` 辞書は `sources` 配列に統合する。M3の `role` には既存 `soumu_urls` のキー（`都市別概況`・`都市別目的別`・`都市別性質別`・`町村別概況`・`町村別目的別`・`町村別性質別`）をそのまま流用する。
- `updated`（UI表示用の更新日、`DataMeta.updated` が消費）と `period` / `year`（データ自体の年度・時点）は系譜メタとは別物として維持する。`fetched_at` はこれらを置き換えない。3つの時刻の意味を混同しないこと（`fetched_at`=いつ取得したか／`period`=データがいつ時点の事実か／`updated`=UIに出す更新日）。

### 5.2 配置方針（確定・decisions #8）

配置は「案B'＝ファイル単位トップレベルの `sources` 配列」で確定する。

- 案A（レコード単位に系譜を複製）は却下。単一ファイルから多数レコードを抽出するM1（42件）・M2（36件）で同一メタの純粋な冗長になる。
- 案B（トップレベルに `source_url` 単数＋hash単数）も却下。M3が6ファイルのマージである以上、単数では表現できない。
- 案B'（`sources` 配列）はM3の6ファイルをそのまま表現し、V2の複数ソース統合JSON（基礎データ層等）も同じ配列で吸収する。単数案との実装差は「配列にするだけ」で、将来のスキーマ破壊を回避できる。

1つのJSON内でレコードごとに由来ファイルが異なるケース（M3の市レコードは市系3ファイル、町村レコードは町村系3ファイル由来）は、必要になった時点でレコード側に `source_ref`（`sources` 配列への軽量参照）を足して対応する。V1では書かない（V2予約）。

#### 5.2.1 多期間ファイルの period 単位配置（2026-09-05 追記・裁定）

§5.2 本文（トップレベル `sources` 配列）は「1ファイル＝単一時点」のデータ（M1〜M3）を前提とする。これに対し、1ファイルが複数期を収録し**各期で取得元ファイルが異なる**多期間ファイル（例：`data/pref_kessan.json`・`data/pref_fiscal_indicators.json` は R6／R5／R4 の決算・指標を1ファイルに持ち、各年度が別の総務省ファイル由来）では、系譜を `periods[].sources`（period 単位の `sources` 配列）として持つ。これは §5.2 本文の逸脱ではなく、本文が想定していなかったケースの正式な拡張である。

- 各 period オブジェクトが自身の `sources` 配列を持ち、その期の数値の由来を表現する。トップレベル単一 `sources` では「どの数値がどの期のどのファイル由来か」を表現できないため、多期間ファイルでは period 単位配置を正とする。
- period 単位 `sources` の各要素の構造は §5.1 のフィールド定義に従う（`role`・`source_url`・`source_page`・`fetched_at`・ハッシュ）。ただし pref 系列のハッシュフィールド名は `source_file_hash_sha256`（M1〜M3系の `source_file_hash` とは別命名。既存の混在を追認する。統一は将来のスキーマ整理課題）。
- 単一時点ファイル（M1〜M3・`pref_governor`・`pref_assembly`・`pref_1a_population` 等）は従来どおりトップレベル `sources` 配列を用いる。多期間ファイルのみ period 単位。ファイルがどちらの形かは、そのファイルが複数期を1レコードに収めるか否かで決まる。
- `content-spec-v1.md` §7.16 残留作業(2)（この配置裁定の要確認事項）は本項をもって解消。

### 5.3 キャッシュ機構下での fetched_at 意味論とハッシュ運用

取得スクリプト（M1〜M3）はいずれも `if cache.exists(): return cache` の単純キャッシュを持つ。通常の再実行ではネットワーク取得が起きないため、`fetched_at` の意味を次のように固定する。

- `fetched_at` は**そのファイルを実際にダウンロードした時刻（原初取得時刻）**とする。スクリプト実行時刻を入れることは禁止（キャッシュヒット時に「取得していないのに取得日時を記録する」嘘になる）。
- `source_file_hash` はキャッシュファイルのバイト列から**毎回 SHA-256 を再計算**する（永続化しない。ファイルから常に導出可能なため）。
- 原初取得時刻の保存は、専用のサイドカー等を新設せず、**git 管理下の自分の前回出力JSON（`data/m1_*.json` 等）を読んで引き継ぐ**方式を取る。実行フロー:
  1. キャッシュファイルから現ハッシュを再計算する。
  2. 既存の出力JSONから、対応する `sources` 要素の旧ハッシュ・旧 `fetched_at` を読む。
  3. **現ハッシュ == 旧ハッシュ**（同一ファイル）→ 旧 `fetched_at` をそのまま引き継ぐ（原初時刻が保存される）。
  4. **現ハッシュ ≠ 旧ハッシュ、または旧記録なし**（新規ファイルまたは上流差し替え）→ `fetched_at` = 現在時刻。
- この機構により、`fetched_at` は「バイト列が変わった時だけ動く」正しい意味論を持つ。専用インフラ（サイドカー・別ファイル）は不要で、追加は3スクリプト共通のヘルパー1つで済む。
- 同時に、ハッシュ不一致の検知が上流ファイル差し替え・訂正の自動アラートを兼ねる（追加コストなし。`docs/operations-runbook.md` 4節の回帰検出と連携する）。

### 5.4 遡及適用（既存M1〜M3）

#8は公開前必須のため、既存M1〜M3にも系譜メタを入れる。ただし**再ダウンロードはしない**（再取得すると `fetched_at` が原初取得時刻でなくなり、5.3の原則に反するため）。

- 既存3JSONの `fetched_at` は現行の手書き `updated`（M1=2026-08-03 / M2=2026-08-06 / M3=2026-07-31）で backfill する。数日精度で原初取得日を近似できる。
- `source_file_hash` は、遡及時点でキャッシュが残っていればそこから算出し、無ければ次回取得時に確定する（以降の差し替え検知の基準点になれば足り、厳密な原初ハッシュは不要）。
- 作業は3JSONへの一度の追記で完了し、継続的な遡及作業は発生しない。旧版の「新規指標追加時からの適用を優先（既存への遡及は避ける）」という方針は、#8が公開前必須かつ対象ソースが小容量・安定 publication（年次/3年次）で再取得コストが実質ゼロである以上、本節で反転させる（遡及を公開前必須とする）。
- 年次データ（M1/M3=年1回、M2=3年ごと）の再取得 cadence は本節の対象外。#8は「過去に取得した事実の記録」であって「どの鮮度で再取得するか」を決めない。鮮度・再取得は #4/#5（`operations-runbook.md` 3〜5節）が持つ。公開後にデータが1年以内に古いことは正常運転であり、#8を薄くしても鮮度は劣化しない（両者は独立）。

### 5.5 全国スケールでの適用範囲

M1〜M3のソースは**全国集約ファイル**（M1のPDFは1,741市区町村収録、M3の6Excelも全国）であるため、対象自治体が42でも1,300でも1,700でも `sources` の要素数は変わらない。系譜メタは自治体数に対して O(1) であり、全国展開に対してスケール不変。ハッシュ差し替え検知も per-file（M1で1回、M3で6回）で一定。

- ただしこの不変性は**ソースが集約ファイルである間だけの性質**である。V2の議会データ（kaigiroku.net）のように自治体ごとに個別取得するソースでは、`source_url`・`fetched_at`・`source_file_hash` が自治体数だけ増える。単一モノリシックJSONのトップレベルに巨大な `sources` 配列を持つ形は破綻するため、per-自治体ファイルへの分割（＋レコードの `source_ref`）へ移行する。5.2で `sources` を配列にしたのはこの移行を最小コストで吸収するための布石。
- 集約ソース系（トップレベル `sources` のみ）と per-自治体ソース系（`sources` + `source_ref`）が混在した際のサイレント破壊は #8単体では防げない。V1の軽量JSON Schema検証（本文書1節・#13）の実在が前提となる。#8の全国耐性は #13 とセットで担保される。
